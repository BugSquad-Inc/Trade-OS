# AI Context System — Complete Guide
## For the Antigravity Agent and Developer

> Read this file once at project start.
> The agent reads it automatically via GEMINI.md after that.
> Do not re-explain this system in every session.

---

## What This System Is

This is your codebase's memory. It sits alongside your code in the same repo.
Every file here answers one question before every coding session:
**"What already exists, and what are the rules?"**

Without this system: AI starts every session blind, rebuilds things that exist,
forgets your patterns, burns tokens re-learning the stack.

With this system: AI reads 450–900 tokens, knows everything relevant, writes
nothing that already exists.

## One-Time Setup (run these once, never again)

```bash
# From project root:

# 1. Create the folders
mkdir -p ai_context/modules

# 2. Install the git hook
cp post-commit .git/hooks/post-commit
chmod +x .git/hooks/post-commit

# 3. Validate CODEMAP.json is readable
python update.py --check

# 4. Generate all files for the first time
python update.py
```

After this, the system is self-maintaining. Every git commit triggers the hook
which triggers update.py which refreshes all ai_context files automatically.

## File Responsibilities

### RULES.md — 15 architectural laws
The non-negotiable rules decided at project start. Things like:
- all notifications go through M6 only, never call Twilio directly
- stock_movements is INSERT ONLY, never UPDATE or DELETE
- no SQL in service.py, no business logic in repository.py

These rules almost never change. If you break one, the architecture breaks.

**Token cost: ~150 tokens. Agent must read this before every single task.**

---

### INDEX.md — module status board
One line per module showing sprint and status. All shared utility names and
file paths. All config key names. Nothing more, nothing detail.

Auto-generated by update.py. Never edit this file manually.

**Token cost: ~300 tokens. Agent must read this before every single task.**

---

### MODULE_X.md files — full module detail
Every function signature, every route, every DB model, every relationship,
every open-source pattern reference — for one module only.

Auto-generated by update.py. Never edit these files manually.

**Token cost: ~400 tokens each. Load only the module being worked on today.**

---

### CODEMAP.json — the source of truth
The raw JSON that all ai_context files are generated from. Agent updates this
after every coding session. update.py reads this to regenerate everything else.

Never paste CODEMAP.json directly into an AI prompt. It is machine data.
Use the generated MODULE files instead.

**You and the agent are responsible for keeping this accurate.**

---

### update.py — the regenerator
Reads CODEMAP.json and regenerates INDEX.md and all MODULE_*.md files.

```bash
python update.py                  # full regeneration — all files
python update.py --module grn     # one module only, faster during active sprint
python update.py --check          # validate CODEMAP.json, write nothing
```

Run this manually after updating CODEMAP.json, or let the git hook do it
automatically on every commit.

---

### post-commit git hook — the automation
Lives at `.git/hooks/post-commit`. Runs automatically after every `git commit`.

What it does:
1. Calls `python update.py`
2. Checks if any `ai_context/` files changed
3. If yes: stages them and amends the commit to include the updates
4. If no: silent, zero noise

The `--no-verify` flag on the amend prevents the hook calling itself in a loop.
If update.py fails (bad CODEMAP.json), the hook warns and exits cleanly —
your commit still goes through. The hook never blocks your work.

**You do not need to run update.py manually if you commit after every session.**

## How Antigravity Uses This System Natively

### GEMINI.md — automatic session start (most important)

Antigravity reads `GEMINI.md` from project root at the start of every agent
session automatically. No prompt, no manual pasting.

Put this in your GEMINI.md:

```
This project uses a structured codebase memory system in ai_context/.

MANDATORY — before writing any code for any task:
1. Read ai_context/RULES.md
2. Read ai_context/INDEX.md
3. Read ai_context/modules/MODULE_{name}.md for the module in today's task
   (if task touches two modules, read both MODULE files)

MANDATORY — after completing any coding task:
1. Update CODEMAP.json with all new entities created
2. Assign the next sequential IMS-{LAYER}-{MODULE}-{SEQ} code to each
3. Run: python update.py

Never write a function, route, model, or utility that already appears
in the MODULE file. If it exists there, call it by its IMS code.
Do not rebuild what already exists.
```

---

### AGENTS.md — cross-tool portability

Same purpose as GEMINI.md but works across all AI tools:
Antigravity, Cursor, Claude Code, Codex.

Put your RULES.md content plus the read-before-coding instruction in AGENTS.md.
Put Antigravity-specific behavior (Plan Mode, Workflows, Deep Think) in GEMINI.md.

When both files exist, GEMINI.md takes priority for conflicting rules.

---

### Skills (.agents/skills/) — on-demand module loading

Antigravity Skills load only when the agent detects they are relevant.
This is exactly how MODULE files should work — on demand, not always.

Create one skill per module:

```
.agents/skills/
├── ims-inventory/
│   └── SKILL.md
├── ims-grn/
│   └── SKILL.md
├── ims-dispatch/
│   └── SKILL.md
└── (one per module)
```

Each SKILL.md contains:

```markdown
---
name: ims-grn
description: Load when building, fixing, or modifying the GRN inbound module (M2).
Triggers on: GRN, goods receipt, inbound, purchase receipt, arrival temp,
QC approval, supplier invoice, OCR capture for GRN.
---

Read this file before writing any code:
ai_context/modules/MODULE_grn.md

This file lists every function, route, and model that already exists in M2.
Do not create anything already listed. Call existing functions by IMS code.
```

Result: when you say "fix the GRN approval flow", the agent automatically
loads the GRN skill, which loads MODULE_grn.md. Zero manual pasting.

### Knowledge Base — persistent backup layer

Antigravity's Knowledge Base persists across sessions even without GEMINI.md.

Add these manually:
- RULES.md content → Knowledge Base item titled "IMS Architecture Rules"
- INDEX.md content → Knowledge Base item titled "IMS Module Index"

How to add: Agent Manager → ⋯ menu → Knowledge Base → Add Item

Update these items whenever RULES.md or INDEX.md changes significantly.
This is a backup — GEMINI.md is the primary mechanism.

### Workflow: /codemap-update — one command end-of-session

Create this workflow in Antigravity to automate the CODEMAP update step.

How to create: Agent Manager → ⋯ → Customizations → Workflows → New Workflow

Workflow instruction:
```
/codemap-update
Update CODEMAP.json with all new entities created in this session.
Assign next sequential IMS-{LAYER}-{MODULE}-{SEQ} code to each new entity.
Run: python update.py
Report which files were updated and how many entities were added.
```

After every session, type `/codemap-update`. The agent handles the full
memory update without you specifying anything.

---

### Plan Mode — use before every new module sprint

Before starting any new module, use Plan Mode. The agent generates a full
Plan Artifact showing every function it will create, which existing IMS codes
it will call, and what the dependency chain looks like.

Prompt for Plan Mode:
```
Read RULES.md, INDEX.md, and MODULE_{name}.md.
Plan the full implementation of [sprint goal].
For each function you plan to create, show its IMS code.
For each existing function you will call, reference its IMS code.
Show the dependency chain: which new functions call which existing ones.
Do not write any code until I approve the plan.
```

Catch duplicate logic at the plan stage, not after 200 lines of code.

---

### Deep Think — use for cross-module tasks

When a task touches two or more modules (example: GRN approval triggering
inventory stock commit), toggle Deep Think on before starting.

The agent reasons through the full dependency chain across both modules before
writing anything. Load all relevant MODULE files first.

---

### Browser Subagents — sprint verification

After each sprint, use Antigravity's browser subagent to test endpoints.

Prompt:
```
Open the browser. Go to http://localhost:8000/docs.
Test these endpoints from this sprint: [paste IMS route codes from MODULE file]
For each: call it, show the response, confirm pass or fail.
Return a summary table of all results.
```

## What to Update After Each Session — Exact Steps

### Scenario 1: Agent added new functions, routes, or models

Ask the agent (or use /codemap-update workflow):
```
Update CODEMAP.json. Add an entry for every new entity created this session.
Assign the next sequential IMS code for each.
Run python update.py after.
```

The agent adds entries → runs update.py → MODULE file refreshes →
next session sees the new functions and will not rebuild them.

---

### Scenario 2: Agent deleted or refactored something

Ask the agent:
```
Update CODEMAP.json. Remove the entries for what we deleted.
Update entries for anything we refactored (signature or behaviour changed).
Run python update.py after.
```

---

### Scenario 3: You committed code (automatic)

The post-commit hook runs update.py automatically.
If ai_context files changed, the hook amends your commit to include them.
Nothing to do manually.

---

### Scenario 4: Plan changed mid-development

1. Tell the agent: "The plan changed. Here is what is different: [explain]"
2. Agent updates CODEMAP.json — removes old entries, adds new ones
3. Agent runs update.py
4. Next session reads the new MODULE file only — no memory of the old plan

Each session reads files, not conversation history.
Plan changes are clean breaks. This is intentional.

---

### Scenario 5: Switched git branches

Nothing extra needed. ai_context files live in the repo.
`git checkout feature/payments` → MODULE files now reflect the payments branch.
`git checkout main` → MODULE files reflect main.
The agent always reads the branch it is currently on.

---

### Scenario 6: Bug fix

Load RULES.md + INDEX.md + the module file for the buggy function.
Fix the bug. If the fix changes the function's interface or behaviour,
update its CODEMAP.json entry and run update.py.
If it is an internal fix that does not change the signature, no update needed.

---

### Scenario 7: New feature added to existing module mid-sprint

Build the feature. At end of session run /codemap-update.
The MODULE file for that module gets the new entity.
Next session: AI sees it exists and will not rebuild it.

## When Agent Tries to Duplicate Something

The MODULE files make duplication visible. If the agent starts building
something already listed:

```
Stop. IMS-{CODE} already exists and does this.
It is in ai_context/modules/MODULE_{name}.md.
Call IMS-{CODE} instead of creating a new function.
```

The more accurate CODEMAP.json is, the less this happens.
Keep CODEMAP.json updated after every session.

## IMS Entity Code Format — Quick Reference

```
Format:  IMS-{LAYER}-{MODULE}-{SEQ}

LAYER codes:
  DB   = database model / table
  SVC  = service function (business logic)
  REP  = repository function (SQL queries)
  RTE  = API route / endpoint
  SCH  = Pydantic schema
  WRK  = background worker / scheduled job
  UTL  = shared utility
  CFG  = config key / env variable
  EVT  = event type
  TST  = test function
  FE   = frontend component / hook
  INF  = infrastructure / docker / nginx

MODULE codes:
  INV  = M1 inventory
  GRN  = M2 GRN inbound
  DIS  = M3 dispatch outbound
  IOT  = M4 IoT cold chain
  BAT  = M5 batch / FEFO
  NOT  = M6 notifications
  RPT  = M7 reports
  OCR  = M8 OCR
  ACC  = M9 accounting
  AUT  = M10 auth
  AIX  = M11 AI gateway
  SHR  = shared utilities

SEQ: 3-digit zero-padded, assigned in order of creation per LAYER+MODULE

Examples:
  IMS-DB-INV-001    Facility model
  IMS-SVC-GRN-002   second service function in GRN module
  IMS-RTE-DIS-003   third route in dispatch module
  IMS-UTL-SHR-001   write_audit_log() shared utility
```

To find next sequence number: check CODEMAP.json, filter by LAYER+MODULE,
take highest SEQ and add 1.

## What This System Prevents

| Problem without system | How system prevents it |
|---|---|
| AI rebuilds a function that already exists | MODULE file lists it, agent calls it instead |
| AI calls Twilio directly from GRN service | RULES.md rule read first, blocks it |
| SQL ends up in service.py | Three-layer rule in RULES.md, read every session |
| Re-explaining the stack every session | GEMINI.md loads context automatically |
| Plan change confuses AI for sessions afterward | CODEMAP.json updated, old entries gone, AI reads new reality |
| Branch switch causes wrong context | ai_context files switch with branch |
| AI duplicates write_audit_log() | MODULE_shared.md shows it exists as IMS-UTL-SHR-001 |
| Notification sent directly from dispatch | RULES.md rule, enforced before any code written |
| Token burn re-reading entire codebase | Load only RULES + INDEX + 1 MODULE = ~850 tokens max |

## Full Daily Workflow

```
MORNING — START SESSION
────────────────────────────────────────
[ ] Open Antigravity
[ ] GEMINI.md loads RULES + INDEX automatically
[ ] Identify today's module from INDEX.md status
[ ] Verify MODULE_{name}.md is current (check last_updated timestamp)

DURING — CODING SESSION
────────────────────────────────────────
[ ] Agent reads MODULE file before writing anything new
[ ] Agent references IMS codes for existing functions it calls
[ ] Cross-module task? Load both MODULE files + use Deep Think
[ ] New sprint? Use Plan Mode first, approve plan before coding starts

END — CLOSE SESSION
────────────────────────────────────────
[ ] Type /codemap-update in Antigravity
    OR ask: "Update CODEMAP.json with everything new, run update.py"
[ ] Confirm MODULE file now includes today's new entities
[ ] git commit → hook runs update.py → ai_context files amend into commit

WHEN SOMETHING CHANGES
────────────────────────────────────────
[ ] Plan change    → update CODEMAP.json first, run update.py, then continue
[ ] Bug fix        → fix code, update CODEMAP.json entry if interface changed
[ ] Feature added  → run /codemap-update at end of session
[ ] Branch switch  → nothing extra, files switch with branch automatically
[ ] Sprint starts  → update INDEX.md module status in CODEMAP.json to IN_PROGRESS
[ ] Sprint done    → update INDEX.md module status in CODEMAP.json to DONE
```
